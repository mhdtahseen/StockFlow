# Ledger Watchtower: Unified Financial Core

## Overview
The **Ledger Watchtower** is a centralized financial monitoring system introduced in MVP 2 to solve the problem of "leaky" finances and inconsistent ledger data. It moves financial recording away from individual UI components and into a centralized, automated logic layer.

---

## 🛑 The Legacy System (Before Watchtower)
Previously, ledger entries were recorded manually inside UI components (e.g., `OrderDetail.tsx`, `PhoneDetail.tsx`).

### Problems Encountered:
1.  **Financial Leaks**: Developers would create a Sale Order but forget to dispatch the `addEntry` call to the Ledger, resulting in orders that existed in the database but showed ₹0 revenue in the financial reports.
2.  **Inconsistent Descriptions**: One screen might log a sale as `"iPhone 13 sold"`, while another logged it as `"Sale #SO821"`. This made searching and auditing nearly impossible.
3.  **Missing Metadata**: Manual calls often missed the `recordedBy` (User ID) or `paymentMode`, making it impossible to know who received the money or via what channel.
4.  **Blank Notes**: Many entries were created with `note: ""` or no note at all, leading to a ledger full of anonymous deductions.

---

## 📡 The Watchtower Solution (After)
The Watchtower uses Redux `extraReducers` to "listen" for business actions across the entire application and automatically log the corresponding financial movement.

### How it Works:
When a business action occurs (e.g., `addOrder` or `addCustomerSettlement`), the Ledger Slice automatically detects it and creates a **Pending Entry** with standardized formatting.

### key Improvements:
| Feature | Legacy System | Watchtower System |
| :--- | :--- | :--- |
| **Automation** | Manual `addEntry` calls | Zero-effort auto-logging |
| **Naming** | Random/Blank notes | **Strict Semantic Pattern**: `[CATEGORY] - [ENTITY] (#ID) : [INFO]` |
| **Audit Detail** | Mixed attribution | Mandatory `recordedBy` and `paymentMode` |
| **Debt Logic** | Debt was invisible | Explicit `DEBT_PLEDGED` vs `CASH_RECEIVED` segregation |

---

## 📝 Semantic Note Standard
Every entry generated by the Watchtower follows this human-readable audit pattern:
- **Pattern**: `[CATEGORY] - [ENTITY] (#REFERENCE) : [DETAILS]`
- **Sale Example**: `SALE - iPhone 13 (#SO-8F2A) : 30% Advance via UPI`
- **Settlement Example**: `SETTLEMENT - Bulk Payment (#PYM-112) : 5 Items Cleared`

## 💻 Code Examples: Before vs. After

### 1. Purchase Confirmation (Manual Leak)
**🛑 BEFORE (Manual & Leaky):**
Located in `PhoneDetail.tsx`, the ledger entry had no description and was easily forgotten.
```typescript
// Manual dispatch inside the UI component
dispatch(addEntry({
  id: crypto.randomUUID(),
  type: "FUNDS_CONSUMED",
  referenceId: phone.id,
  amount: -finalPrice,
  createdAt: now,
  // Note is missing! metadata is missing!
}));
```

**✅ AFTER (Watchtower & Protected):**
The Watchtower listens for the `addPurchaseOrder` action and logs it automatically with consistent metadata.
```typescript
// In ledger/slice.ts (Central Watchtower)
builder.addCase(addPurchaseOrder, (state, action) => {
  const po = action.payload;
  state.pendingEntries.push({
    type: "FUNDS_CONSUMED",
    purchaseOrderId: po.id,
    amount: -po.amountPaid,
    note: `PURCHASE - #${po.id.slice(0, 8).toUpperCase()} : Advance Payment`,
    recordedBy: po.recordedBy || 'system'
  });
});
```

### 2. Repair Logging (Random & Inconsistent)
**🛑 BEFORE (Random String):**
```typescript
// Manual string entry leads to "Repair", "Fix", "Screen" inconsistencies.
note: repairNote.trim() || "Repair" 
```

**✅ AFTER (Semantic Pattern):**
```typescript
// Enforced structure ensures audits are easy to read.
note: `REPAIR - ${phone.brand} ${phone.model} : ${repairNote.trim() || 'General Maintenance'}`
```

## 💰 Specialized Automation Logic

The Watchtower handles complex financial scenarios with zero manual intervention:

### 1. Overpayment & Advance Credits
When a customer pays more than the total owed across all allocations:
- **Calculation**: `Excess = Total Received - Sum of invoice allocations`.
- **Audit Split**: The Watchtower logs **two** distinct entries:
    - `DEBT_SETTLEMENT`: Clears the existing invoice debt.
    - `ADVANCE_RECEIVED`: Marks the remainder as a credit balance.

### 2. Repair Automation [NEW]
The Watchtower now listens for the `addRepairLog` event. When a repair is logged on a device:
- **Ledger Entry**: Automatically created as `REPAIR_COST`.
- **Amount**: Automatically negated (Cash Out).
- **Semantics**: Note is formatted as `REPAIR - #PHONE_ID : Description`.

### 3. Asset Adjustment & Price Drift [NEW]
If a phone's purchase price is manually edited (e.g., via `EditPhone`):
- **Watchtower Action**: It compares the `prevPrice` with the `newPrice`.
- **Ledger Entry**: Automatically logs an `INVENTORY_ADJUSTMENT`.
- **Integrity**: Ensures the "Stock Value" on the dashboard always matches the historical ledger truth.

### 4. Automated Rejection-Cost Offsets
When a unit is marked as `REJECTED` in a Purchase Order:
- **PO Total**: Decrements automatically to remove the cost of the rejected unit.
- **Refund Due**: A `SUPPLIER_PAYMENT` (positive) entry is logged, indicating the vendor owes a credit for the already-paid-for unit.

---

## 🛡 Verification & Integrity
By centralizing the logic, we ensure:
1.  **Atomic Integrity**: A sale cannot exist without a ledger record.
2.  **Landed Cost Accuracy**: P&L calculations automatically factor in Purchase Price + Repairs because the Watchtower tracks both.
3.  **Debt Reconciliation**: Advances are automatically subtracted from "Total Receivables," ensuring your Net Worth reflects real cash positions.
4.  **TWA Performance**: Offline entries are queued and synchronized with the same semantic standards, ensuring no data loss on Android devices.
